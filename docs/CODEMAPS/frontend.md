# 프론트엔드 코드맵

**마지막 갱신:** 2026-08-22
**진입점:** `frontend/src/main.tsx` → `App.tsx` → `features/workspace/WorkspacePage.tsx`

React 19 + TypeScript + Vite 단일 페이지 앱. **캔버스는 미리 그려 둔 삼각형 층을 얹는다.** 단면의 삼각형이 nmos 8,813개,
cmos 16,248개다. 커서를 옮길 때마다 다시 칠하면 손에 걸리므로, 구조와 캔버스
크기가 그대로면 한 번 그려 두고 `drawImage` 로 얹기만 한다
(`plot/SurfaceView.tsx`, `features/devsim/ElectrodeMap.tsx`).

그 위쪽에서는 **memo 의존성을 좁게 잡는다.** `spec` 통째에 매달면 전압을 한
글자 칠 때마다 새 참조가 되고, 내용이 안 바뀌었는데도 다시 그리기로 번진다 —
실제로 그렇게 됐다. 읽는 부분(`spec.electrodes`, `spec.interface_names`)에만
매단다.

라우터가 없다. 화면은 **공정**과 **소자 해석** 둘뿐이고 `App.tsx` 의 상태
하나(`view`)로 갈린다. 옮길 때 **묻지 않는다** — 잡은 서버에서 돌고 두 화면
모두 `hidden` 으로 감출 뿐 내려놓지 않으므로 옮겨도 잃는 것이 없다. 도는
중이라는 것은 탭의 점(●)으로 알린다.

---

## 1. 진입점: 사용자가 "실행"을 누르면

```
WorkspacePage.run()
   │
   ├─ dirty 면 먼저 save()          ★ 저장과 실행을 분리하되, 실행 전엔 반드시 저장
   │     └─ files.write(path, source)   → PUT /api/files/content
   │
   ├─ files.run(path)                   → POST /api/files/jobs
   └─ setJobId(job.id)
          │
          ▼
   JobPanel(jobId)
   └─ useJob(jobId)                 1.5초 폴링, 종료 상태면 멈춘다
         ├─ jobs.get(id)                → GET /api/jobs/{id}      상태·진행·산출물
         └─ jobs.console(id)            → GET /api/jobs/{id}/console
                                          ★ 끝났을 때 **한 번만**. 로그는 폴링에
                                            싣지 않는다 (아래 `useJob`)
                │
                ▼ artifacts 가 생기면
         ResultView(jobId, artifacts)
           │
           ├─ useSettled(sequence, 250ms)   ★ 단계를 빠르게 넘길 때 중간 단계는 안 받는다
           │
           ├─ plot.summary(job, seq)        → .../structure   무엇을 그릴 수 있나
           ├─ plot.profile(job, seq, q, x)  → .../profile     고른 물리량마다 하나씩
           └─ plot.surface(job, seq, q)     → .../surface     2D 일 때만
                │
                ├─ ProfileChart (SVG)   깊이 프로파일, 로그 축, 재질 배경 띠
                └─ SurfaceView (canvas) 2D 단면 + 컷 선 + 선택적 격자 오버레이
```

오류는 전부 `api/client.ts` 의 `ApiError` 로 올라오고, 401 이면 화면이 즉시
로그아웃 상태로 되돌아간다(`AuthContext.clear`). 세션이 서버에서 만료돼도
브라우저는 그것을 알 방법이 없으므로 이 경로가 유일한 복구 수단이다.

## 2. 화면 구조

```
┌─────────────────────────────────────────────────────────────┐
│ header   TCAD │ 파일 탭들 │ 파일 열기 │ 이메일 관리자 로그아웃│
├─────────────────────────────────────────────────────────────┤
│ toolbar  저장(•) │ 실행 │ 매뉴얼 │ 메시지                     │
├──────────────────────┬────────┬──────────┬────────┬─────────┤
│                      │        │          │        │         │
│  SupremEditor        │Splitter│ DocsPanel│Splitter│ JobPanel│
│  (Monaco)            │        │ (선택)   │        │  ├ 로그 │
│                      │        │          │        │  └ 결과 │
└──────────────────────┴────────┴──────────┴────────┴─────────┘
   ▲ 모달: FileBrowser (파일 열기), AdminPanel (관리자)
```

`WorkspacePage` 가 열어 둔 파일 탭·활성 파일·소스·현재 잡을 들고 있는 유일한
지점이다. 상태 관리 라이브러리가 없다 — 공유해야 할 상태가 이 하나뿐이라
prop 으로 내려보내는 것으로 충분하다.

탭은 **"내가 연 파일"** 이지 작업공간 전체가 아니다. 만들고 지우고 이름 바꾸는
일은 `FileBrowser` 에서 하고, 탭을 닫아도 파일은 남는다.

소자 해석 화면은 위쪽에 고른 보관 구조와 폴리 게이트 처리 방식을 두고, 그
아래를 둘로 나눈다 — 왼쪽에 단면(`ElectrodeMap`, 거기서 계면을 골라 전극에
붙인다)과 전극·전압원 편집(`SourceEditor`), 오른쪽에 실행 버튼과 진행·곡선
(`RunResult`). "비교" 탭으로 넘기면 저장해 둔 해석들을 겹쳐 보는 `CompareView`
가 그 아래 전체를 대신한다. 가운데 `Splitter` 는 작업 화면과 같은 훅
(`usePanelWidth`)을 쓴다.

## 3. 구획별 책임

### `src/api/` — 백엔드 경계

| 파일 | 책임 |
|---|---|
| `client.ts` | `fetch` 한 겹. 오류를 `ApiError{status, detail}` 로 정규화 |
| `endpoints.ts` | 경로 문자열을 이름 있는 함수로 감싼다 (`auth`, `files`, `editor`, `jobs`, `plot`, `devsim`, `docs`, `admin`, `projects`) |
| `types.ts` | 응답 타입. `JobDetail`(상태)과 `JobConsole`(실행 출력)이 **나뉘어 있다** |
| `catalog.ts` | 카탈로그 전용 캐시 (아래 참조) |

인증은 **httponly 세션 쿠키**다. 토큰을 JS 가 들고 있으면 XSS 한 번에 새므로
브라우저가 알아서 실어 보내게 두고 코드는 손대지 않는다. 그 대신 요청이 반드시
같은 출처로 나가야 해서, 개발 중에는 Vite 프록시(`/api` → 백엔드)를 쓴다. CORS
설정을 열 필요가 없다.

`client.ts` 가 상태 코드별 한국어 문구를 갖고 있는 이유: 프록시가 막은 응답은
본문이 JSON 이 아니라 상태 코드밖에 단서가 없다. 숫자만 보여주면 사용자는
서버 고장인지 자기 탓인지 알 수 없다.

`catalog.ts` 는 별도 캐시를 둔다. 자동완성은 키 입력마다 불리는데 카탈로그는
배포 중에 바뀌지 않으므로 한 번 받아 두고 걸러 쓴다. 진행 중인 요청을 그대로
들고 있어 겹친 호출이 하나로 합쳐진다.

### `src/features/` — 도메인별 화면

```
auth/       AuthContext (로그인 상태), LoginPage (로그인 + 초대 가입),
            useOccupancy (접속 현황 30초 폴링)
workspace/  WorkspacePage (본체), panelLayout, usePanelWidth,
            editorSession (탭·초안·커서 규칙), useEditorSession (서버 연결)
files/      FileBrowser (모달, 드래그 이동 지원), tabLabels
editor/     SupremEditor (Monaco 래퍼)
jobs/       JobPanel (상태·실행시간·공정진행·로그·중단), useJob (폴링 + 출력),
            useElapsed (실행 시간 이어 세기), duration (시간 표기)
devsim/     DevSimPage (본체), SourceEditor (전극·전압원 편집), ElectrodeMap
            (단면에서 계면 고르기), RunResult (진행·곡선·중단), CompareView
            (저장한 해석 비교·삭제), IvChart, FigureTable, NameField,
            NumberField, deviceSpec (스펙 규칙), figures, hitTest, specDiff
docs/       DocsPanel (매뉴얼/파라미터/레퍼런스 3탭), ParameterTable, ReferenceBrowser
admin/      AdminPanel (초대 발급·회수)
```

각 폴더가 "한 가지 일"을 맡고 서로를 직접 부르지 않는다. 예외는 `WorkspacePage`
로, 이들을 조립하는 자리라 대부분을 임포트한다.

몇 가지 설계 근거:
- **`AuthContext`** — 세션이 httponly 쿠키라 JS 는 "로그인했는가"를 서버에
  물어야만 안다. 최초 확인이 끝나기 전에 로그인 화면을 띄우면 이미 로그인한
  사용자에게도 한 번 깜빡이므로 `loading` 상태가 따로 있다.
- **`FileBrowser`** — 폴더와 `.in` 만 보인다. 서버도 같은 규칙으로 거르지만
  화면이 규칙을 알아야 새 파일 이름에 `.in` 을 붙여 줄 수 있다. 드래그 이동은
  서버의 rename 엔드포인트를 그대로 쓴다 — 이름 바꾸기와 옮기기가 같은 연산이라
  새 엔드포인트가 필요 없다.
- **`tabLabels`** — 보통은 파일 이름만, 다른 폴더에 같은 이름이 있을 때만
  **구분될 만큼만** 경로를 앞에 붙인다. 전체 경로를 늘 붙이면 탭이 길어져 정작
  이름이 안 보인다.
- **`JobPanel.runLabel`** — 잡 번호는 전체 사용자가 공유하는 기본키라 혼자 두 번
  돌려도 건너뛴다(#23 다음이 #27). 그래서 "경로 · 제출 시각"으로 가리킨다.
- **`editorSession`** — 탭 전환에 저장을 요구하지 않는 근거가 여기 있다.
  고치던 내용은 버퍼에 남고, 돌아오면 그대로 이어서 고친다. 저장은 곧 "실행
  대상이 바뀐다"는 뜻이라 잠깐 다른 파일을 들춰 보려고 시킬 일이 아니다.
  **닫을 때는 묻는다** — 전환과 달리 버퍼를 버리므로 되돌릴 수 없다.
- **`useEditorSession`** — 들어올 때 서버에서 되살리고, 바뀌면 1초 뒤 한 번
  남기고, **보려는 탭만** 읽어온다. 되살리기가 끝나기 전에는 아무것도 남기지
  않는다 — 빈 상태를 먼저 보내면 서버에 있던 탭 목록을 지운다. 스무 개를
  한꺼번에 읽으면 nginx 레이트 리밋(20 req/s)에 그대로 걸린다.
- **`SupremEditor` 의 `path`** — Monaco 에 경로를 넘기면 파일마다 모델이
  따로 생긴다. 되돌리기 기록이 파일별로 나뉘고(탭을 옮긴 뒤 Ctrl+Z 가 남의
  파일을 되돌리지 않는다) 보던 줄도 탭마다 보존된다. `keepCurrentModel` 은
  탭을 처음 열 때 내용을 받아오는 동안 편집기가 잠깐 내려가는데, 그때 모델이
  버려지면 그 파일의 되돌리기 기록이 사라지기 때문에 켠다.
- **`ResultView` 의 첫 단계** — **마지막 단계부터 보여준다.** 보려는 것은 보통
  공정이 끝난 모습이고, 25단계짜리 흐름에서 거기까지 '다음' 을 스물네 번 눌러
  가는 것은 번거롭다. 실패한 실행에서도 마지막 산출물이 곧 마지막으로 성공한
  단계다. 되돌리는 effect 의 의존성은 배열이 아니라 **길이와 잡 번호**다 —
  폴링이 1.5초마다 같은 내용의 새 배열을 만들기 때문에, 배열을 걸면 앞 단계를
  볼 때마다 마지막으로 끌려간다.
- **`useElapsed`** — 실행 시간의 **시작값은 서버가 계산해서 준다.** 브라우저가
  제출 시각과 자기 시계를 빼서 구하면 시계가 어긋난 만큼 그대로 틀린다. 화면은
  그 값에 흐른 시간만 더하고(차이만 쓰므로 시계 오차와 무관), 다음 폴링이 다시
  맞춘다. 끝난 잡은 멈춰야 총 실행 시간이 고정된다.
- **공정 진행** — 로그는 실행이 끝나야 도착한다. 그때까지 "실행 중" 세 글자만
  보이면 53단계 흐름이 도는 것인지 멈춘 것인지 알 수 없다. 서버가 작업디렉토리의
  `.str` 을 세어 "oxidation.str 완료 · 7/15" 를 준다. **끝난 잡에는 주지 않으므로**
  화면에서 따로 지울 필요가 없다.
- **`useOccupancy`** — 접속 현황은 30초마다 본다. 사람이 드나드는 빈도라 잡
  상태(1.5초)만큼 자주 볼 이유가 없다. 실패해도 마지막 값을 지우지 않는다 —
  잠깐 끊겼다고 숫자가 사라지면 화면이 깜빡인다.
- **중단 버튼** — 대기/실행 중일 때만 뜬다. 서버 응답을 기다리지 않고
  `applyStatus` 로 상태를 먼저 반영한다 — 다음 폴링(1.5초)까지 "실행 중"으로
  보이면 눌린 것인지 알 수 없다. 폴링이 곧 같은 값을 확인해 준다. 소자 해석
  (`RunResult`)도 같은 버튼을 갖는다. 잡 종류가 달라도 큐·중단은 한 벌이라
  `jobs.cancel` 을 그대로 쓴다.
- **`useJob` 의 출력(`console`)** — 상태와 **따로** 받는다. 상태 조회는 1.5초
  마다 다시 부르는데 거기에 로그가 실려 있으면 폴링마다 실행 출력 전체가
  따라온다(실측 97KB). 그 크기가 nginx 프록시 버퍼를 넘겨 응답을 깨뜨렸고,
  브라우저는 완료를 영영 감지하지 못한 채 끝난 잡을 6분 넘게 다시 물으며
  "연결이 불안정합니다" 를 띄웠다. 로그는 잡이 끝날 때 한 번 기록되므로
  **끝났을 때 한 번만** 받는다. 받다가 실패해도 `error` 를 세우지 않는다 —
  로그는 곁다리라, 그것 때문에 멀쩡히 끝난 잡이 실패한 것처럼 보이면 안 된다.
  잡이 바뀌면 앞의 출력을 지운다(남기면 새 잡 화면에 옛 로그가 잠깐 보인다).
  `JobPanel` 의 로그 칸과 "로그 전문 내려받기" 안내, `RunResult` 의 실패 로그가
  모두 이 값을 쓴다.
- **`DocsPanel`** — 기본 동작은 **커서를 따라가는 것**이다. 편집기 커서가 놓인
  줄의 커맨드 문서를 자동으로 띄운다. 접두사 해석(`stru` → `structure`)은 서버가
  한다 — 시뮬레이터가 그렇게 받아들이므로 문서도 같아야 한다.
- **`AdminPanel`** — 평문 초대 코드는 발급 응답에서만 볼 수 있다(서버가 해시만
  저장한다). 그래서 발급 직후 크게 띄우고 다시 볼 수 없다는 사실을 분명히 말한다.

소자 해석 화면에서 따로 알아야 할 것:
- **입력칸이 치는 동안의 글자를 직접 들고 있다.** 값을 매 글자마다 바깥에서
  받아 다시 넣으면 중간 상태가 살아남지 못한다. 숫자 칸(`NumberField`)은
  `"0."` 이 `0` 을 거쳐 `"0"` 으로 되돌아가 소수점을 못 치는 것으로 드러났고,
  이름 칸(`NameField`)은 그보다 나빴다 — 이름이 곧 목록 항목의 `key` 라 한
  글자마다 항목이 새로 만들어지면서 입력칸이 포커스를 잃어 **한 글자밖에 못
  쳐졌다.** 알리는 시점만 서로 다르다: 숫자는 숫자로 읽히는 동안 곧바로,
  이름은 칸에서 벗어날 때(또는 Enter) 한 번. 이름을 늦추는 이유는 치는 도중의
  이름이 다른 이름과 겹칠 수 있기 때문이고, Escape 는 되돌린다. 바깥이 받아
  들이지 않으면 값이 그대로 돌아오므로 칸도 원래 이름으로 되돌아간다 —
  덕분에 지웠다 다시 쓰는 것도 된다(예전에는 빈 이름을 거절하는 바람에 화면이
  옛 이름으로 되돌아가 지울 수가 없었다).
- **목록의 `key` 를 이름으로 삼지 않는다.** 이름은 사용자가 고치는 값이라
  신원이 될 수 없다. 전극과 전압원은 순서가 바뀌지 않으므로 자리 번호로
  충분하다. (위 결함의 나머지 절반이 이것이었다.)
- **짜 둔 조건을 서버에 맡긴다.** 전극에 이름을 붙이고 계면을 붙이고 전압을
  정하는 데는 손이 꽤 가는데 새로고침 한 번에 전부 초기값으로 돌아갔다. 한
  글자마다 보내지 않고 1초 기다렸다 한 번 보내며(편집기 상태와 같은 값),
  **받아 오는 중에는 보내지 않는다** — 기본값이 맡아 둔 조건을 덮어쓴다.
  맡아 둔 것이 없거나 지금 구조에 안 맞으면 서버가 404 를 주고 화면은 기본값
  으로 시작한다. 창 폭 같은 화면 취향은 그대로 브라우저(localStorage)에 둔다 —
  데이터는 서버, 취향은 브라우저.
- **`CompareView` 의 삭제는 되돌릴 수 없다.** 그래서 먼저 묻는다. 곡선이 잡
  산출물에도 남아 있긴 하지만 그쪽은 청소에 지워지므로, 여기서 지운 것은
  사실상 사라진다. 지우면 목록·선택·불러온 데이터에서 모두 치우고, 서버가
  이미 없다고 해도(404) 화면에서는 치운다.

### `src/plot/` — 결과 렌더링

외부 차트 라이브러리를 쓰지 않는다. 필요한 것이 특이하고(로그 축 + 재질 구간
분할 + 부호 전환) 삼각형 수천 개를 그려야 해서 직접 그리는 편이 짧다.

| 파일 | 책임 |
|---|---|
| `ResultView.tsx` | 단계 이동, 물리량 선택, 세 API 호출 조율 |
| `ProfileChart.tsx` | 깊이 프로파일 (SVG) |
| `SurfaceView.tsx` | 2D 단면 (canvas) |
| `scale.ts` | 로그 정의역·눈금·값→색 |
| `segments.ts` | 프로파일을 재질·부호 구간으로 끊기 |
| `surfaceGeometry.ts` | 단면 좌표 변환·눈금 (그리기와 클릭이 공유) |
| `zoom.ts` | 가로축 확대·이동 |
| `materials.ts` | 재질 색 팔레트 |

**SVG 와 canvas 를 나눠 쓴다.** 프로파일은 선 몇 개라 SVG 가 다루기 쉽고,
단면은 삼각형 수천 개라 SVG 로 하면 DOM 노드가 그만큼 생겨 컷 선을 끄는 동안
브라우저가 버티지 못한다.

**물리량 고르기가 두 군데로 나뉘어 있다.** 보는 대상이 다르기 때문이다:
2D 단면은 값을 색으로 칠하므로 콤보박스 하나(한 번에 하나만 의미가 있다),
수직선 프로파일은 체크박스 여럿(chem 과 active 를 나란히 봐야 활성화 정도를
알고, net_doping 을 겹쳐야 접합이 보인다). 한 상태로 묶으면 단면 색을 바꾸려다
그래프가 통째로 바뀐다.

그래프 쪽에서 물리를 지키는 규칙들:
- **선을 재질 경계에서 끊는다.** 계면에서 값이 실제로 불연속이라 이어 그리면
  물질 경계가 농도 급락처럼 보인다.
- **재질은 배경 띠, 물리량은 선 색.** 재질을 선 색으로 쓰면 물리량에 쓸 색이
  남지 않는다.
- **부호 있는 값은 절댓값을 로그 축에 올리고 음수 구간을 점선으로 구분한다.**
  net_doping 은 p 형 구간에서 음수인데 버리면 그래프가 통째로 빈다. 부호가
  바뀌는 자리가 곧 접합이다.
- **가로축만 확대한다.** 세로 눈금이 확대할 때마다 바뀌면 단계를 오갈 때 높이를
  비교할 수 없다.
- **재질 보기가 기본**이고 이때는 서버에 물리량을 보내지 않는다. 보내면 서버가
  그 물리량의 해가 없는 요소를 버려 층이 통째로 빠진다.
- 1D 배경 띠와 2D 단면이 **같은 재질 색 체계**를 쓴다(톤만 다르다). 두 화면을
  오갈 때 같은 층인지 알아보려면 필요하다.

### `src/components/` — 공용 훅·부품

| 파일 | 책임 |
|---|---|
| `Splitter.tsx` | 드래그·키보드로 패널 폭 조절, 폭 clamp 규칙 |
| `useHoldRepeat.ts` | 꾹 누르면 반복 (공정 단계 이전/다음) |
| `useSettled.ts` | 값이 멎을 때까지 기다렸다 알림 |

`useHoldRepeat` 은 키보드 자동반복과 같은 규칙이다 — 누르는 순간 한 번, 400ms
뜸을 들인 뒤 150ms 주기로 반복. 뜸이 없으면 평범한 클릭 한 번이 두세 번으로
번진다. **떼는 것은 버튼이 아니라 창에서 듣는다**: 끝에 닿으면 버튼이 비활성이
되는데 비활성 버튼은 `pointerup` 을 주지 않아 반복이 안 멈춘다.

`useSettled` 는 그 반복과 짝을 이룬다. 단계를 빠르게 넘길 때 지나치는 단계마다
서버에 물으면 단계당 요청 3~4개가 그대로 곱해져 nginx 레이트 리밋에 걸려 503 이
난다. 화면 번호와 파일 이름은 즉시 바뀌고(누른 것이 느껴져야 한다) 데이터만
250ms 멎은 뒤 한 번 받는다. 첫 값은 늦추지 않는다.

`Splitter` 의 폭 규칙은 **편집기를 살리는 쪽**으로 기운다. 창이 좁아 하한을 다
지킬 수 없으면 패널을 깎는다 — 이 도구의 본체는 편집기다. 여러 패널이 함께
열렸을 때의 조정은 `features/workspace/panelLayout.ts` 가 맡는다: 손잡이는 자기
패널만 보므로 각자 옳아도 합이 창을 넘길 수 있고, 넘치면 `minmax(0, 1fr)` 인
편집기 칸이 소리 없이 0 으로 접힌다.

### `src/suprem/` — 에디터 언어 통합

| 파일 | 책임 |
|---|---|
| `monacoSetup.ts` | Monaco 를 로컬 번들에서, 필요한 기여(contrib)만 골라 로드 |
| `language.ts` | Monarch 토크나이저 + 언어 설정 (`.in` 문법) |
| `context.ts` | 커서 위치에서 무엇을 완성해야 하는지 판정 |
| `providers.ts` | 자동완성·호버 제공자 등록 |
| `docs.ts` | 호버에 띄울 마크다운 생성 |

여기에 함정이 몇 개 있어서 주석이 길다:
- **CDN 을 쓰지 않는다.** `@monaco-editor/react` 기본값은 jsdelivr 인데, 자체
  호스팅 서비스에서 그대로 두면 외부 망이 끊길 때 편집기가 아예 안 뜨고 사용자
  접속 사실이 제3자에게 샌다.
- **`editor.api` 만으로는 안 된다.** API 표면만 있고 자동완성 위젯·호버 같은
  기여가 빠져서, 제공자를 등록해도 Monaco 가 한 번도 부르지 않는다. 등록은
  성공하고 언어도 맞는데 자동완성만 조용히 죽는다. 그렇다고 `editor.main` 을
  쓰면 80여 개 언어 정의와 TypeScript 언어 서비스까지 딸려 온다. 그래서
  **쓰는 기여만 명시적으로** 임포트한다. Monaco 를 올릴 때 이 목록이 깨질 수 있다.
- **등록은 `beforeMount` 에서 한다.** `onMount` 는 모델이 이미 만들어진 뒤라
  언어가 plaintext 로 잡히고, 나중에 제공자를 등록해도 그 모델에는 안 붙는다.
- 접두사 해석은 프론트가 하지 않는다. 모호함을 판정하려면 전체 이름 집합이
  필요하므로 사용자가 친 그대로 서버에 넘긴다.

Monaco 를 포함한 작업 화면 묶음이 약 3.2MB 라 `App.tsx` 에서 `WorkspacePage` 를 `lazy` 로 나눠 로그인한
뒤에 받는다.

## 4. 테스트

```
src/**/*.test.ts(x)   Vitest + Testing Library. API 와 Monaco 를 목으로 가린다.
e2e/*.spec.ts         Playwright. 진짜 브라우저로 진짜 백엔드를 친다.
```

경계가 분명하다. 단위 테스트는 로직(폭 계산, 라벨 짓기, 로그 축, 구간 분할,
커서 문맥 판정)을 보고, **E2E 만이 확인할 수 있는 것**이 따로 있다:

- Monaco 가 브라우저에서 실제로 뜨는가 (jsdom 에서는 뜨지 않는다)
- 자동완성이 카탈로그 API 를 타고 오는가
- 세션 쿠키가 브라우저에 실리고 새로고침 뒤에도 살아 있는가
- 제출한 잡이 워커를 거쳐 진짜 컨테이너에서 돌아 결과가 돌아오는가
- HTML5 드래그가 실제로 붙는가
- 그리드가 넘쳐 편집기 칸이 0 으로 접히지 않는가

`e2e/global-setup.ts` 가 **임시 PostgreSQL DB 를 만들어 마이그레이션을 걸고**
API 와 워커를 띄운다. 개발 DB 를 쓰면 테스트가 남긴 계정·잡이 쌓이고 반대로
개발 데이터가 결과를 흔든다. `workers: 1` 인 이유는 동시 접속 정원과 잡
큐를 공유하기 때문이다. 캔버스는 jsdom 에서 그릴 수 없어 그리기 자체는 단위
테스트가 안 되고, 그래서 좌표 수식만 `surfaceGeometry.ts` 로 떼어 두었다.

## 5. 빌드·실행

```bash
npm run dev       # Vite 개발 서버, /api 는 TCAD_API_URL(기본 127.0.0.1:8000)로 프록시
npm run build     # tsc -b && vite build
npm run test      # Vitest (e2e/ 는 제외)
npm run coverage
npm run e2e       # Playwright (백엔드를 스스로 띄운다)
npm run lint      # oxlint
```
